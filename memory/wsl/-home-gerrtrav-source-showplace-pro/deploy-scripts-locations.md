Neither deploy script is in the repo; read them over SSH (hosts `prodev` and `proprod` in ~/.ssh/config).

- **Staging (`prodev`):** `/srv/git/showplace_pro.git/hooks/post-receive` (bare repo shared via group `www-data`, `core.sharedRepository=group`; was `~/repos/` before 2026-10-07), which runs on `git push prodev master` (see [[staging-remote-prodev]]). Builds with `yarn run dev`, then runs `migrate --force` and a supervisorctl reload. The 2026-10-01 version is saved as `post-receive.bak-20261001`. The hook uses `sudo -n` per /etc/sudoers.d/showplace-pro-deploy and chowns the work tree to the pushing user (`$(id -un)`, changed from hardcoded travisgerry on 2026-10-07; backup `~/post-receive.bak-20261007`). Other developers can deploy only if that sudoers file covers them. Since 2026-10-14 (SPPRO-4982) the hook pins `PHP=/usr/bin/php8.5` and runs `"$PHP" /usr/local/bin/composer install` and `"$PHP" artisan migrate`, independent of the `php` alternative (backup `~/post-receive.bak-20261014`); staging workers link `resources/workers/supervisor/staging/` (php8.5) while prod keeps the root configs (php8.2). Composer on prodev is 2.10.3. On 2026-10-15 (SPPRO-4984) Laravel Excel was replaced by PhpSpreadsheet 5.10 (supports PHP 8.2-8.5), so the hook's composer runs on 8.5 with no platform override (temporary `--ignore-platform-req=php` removed; backup `~/post-receive.bak-20261015`). If a deploy fails after `git reset`, the hook leaves new code without vendor/assets/migrations and `public/p3ordfiles` deleted; restore with `ln -sfn /var/www/pro/p3ordfiles /var/www/showplace_pro/public/p3ordfiles`. Node v16.20.2 as of 2026-10-06, installed from the NodeSource apt repo (`/etc/apt/sources.list.d/deb_nodesource_com_node_16_x.list`), so apt never moves it past 16; changing it needs the user's sudo password. Target is Node 22 on both servers (SPPRO-4818 prodev, unassigned, still v16 on 2026-10-15, upgrade commands in its comment; SPPRO-4873 prod, Shad); local Sail is 22 and the user is fine leaving it there as long as builds work on 22.
- **Production (`proprod`):** `/usr/local/bin/update_showplace_pro` (owned by root, run by hand as travisgerry). Order: `sudo chown -R travisgerry` the app, `git reset --hard`/`clean -df`/`pull --rebase`, (`composer install --no-dev` is commented out as of 2026-10-20), `yarn install`, `yarn run prod`, then `sudo chown -R www-data:www-data` and the `p3ordfiles` symlink. Runs ~06:30 daily. While the tree is owned by travisgerry (~40s), web requests can't write storage: Nightwatch issue 468 (iconify `storage/app/icons/mdi`, mode 700, 500 on /login to the Better Stack uptime bot) fired at 06:29 on 2026-10-06 and 06:34 on 2026-10-20, both mid-deploy. It does NOT run migrations or restart workers. Node v20.20.2 as of 2026-10-06.
  - Until 2026-10-12 the chown to www-data ran *before* the build. Yarn (as travisgerry, only in the www-data group) can't chmod files that www-data owns, so `yarn install` died with `EPERM ... chmod node_modules/.../.bin/...`, left no `node_modules/.bin` and no `.yarn-integrity`, and `yarn run prod` failed with `/bin/sh: 1: mix: not found`. Prod's JS had not been rebuilt since 2026-09-02. The user moved the chown to after the build that day and rebuilt. If it recurs, check the order in the script and who owns `node_modules`. The fix is to `sudo chown -R travisgerry` node_modules, run `yarn install`, then hand the tree back to www-data.
  - Webpack 5 doesn't rewrite unchanged output, so an asset's old mtime after a good build (e.g. `public/assets/css/app.css`) isn't proof the build failed. Grep its contents instead.
- Both run `git clean -df` without `-x`, so gitignored build output survives deploys.

The Mix → Vite migration (epic SPPRO-4814) depends on these: keep a `prod` script alias so the production script needs no change, switch the prodev hook to `yarn run build`, and upgrade Node on prodev first (SPPRO-4818).

Editing the staging app's env (`/var/www/showplace_pro/.env` on `prodev`, owned www-data, mode 664): `sudo` needs a password there, but the user `travisgerry` is in the `www-data` group, so edit it without sudo. Rewrite it in place (`sed ... > /tmp/x && cat /tmp/x > .env`) rather than `sed -i`, so it keeps www-data ownership. Keep backups in `~` (chmod 600), not the app dir: the deploy's `git clean -df` deletes untracked, non-ignored files like `.env.bak-*`. No config cache is used, so env changes apply without `config:clear`. Feature flags for staging rollout go in as the all-users `FEATURE_<NAME>_ENABLED=true` line, next to the other flags (done for SPPRO-4587 on 2026-10-06 and SPPRO-4850 on 2026-10-07; verify with `php artisan tinker` over ssh that config and Feature::active return true). On 2026-10-08 (SPPRO-4585) the auto-mode classifier blocked this remote .env edit, but later that day (SPPRO-4584) the user said "you can update prodev .env file", so do the edit yourself: `ssh prodev` backup to `~/env.bak-<ticket>` (chmod 600), then append the line with `>>` (keeps www-data ownership). Verify through the browser driver (e.g. quote form Livewire snapshot) rather than artisan tinker, see [[prodev-tinker-breaks-cache-perms]].
